[00:02:05] Interviewer: Can you explain the internal trade-offs between B-tree indexes and hash indexes in PostgreSQL, and how you decided which to use?
[00:02:22] Candidate: B-tree is PostgreSQL's default because it maintains sorted order, supporting equality as well as range queries, prefix matching, and ORDER BY clauses with logarithmic time complexity O(log N). Hash indexes only support single equality operators (=) and do not support range scans or ordering. For our time-series partitioned order tables, B-tree indexes on composite keys (tenant_id, created_at) were essential for fast range scans in analytical queries.

[00:03:55] Interviewer: What happens if a Kafka consumer group encounters a poisoned message that repeatedly fails to deserialize or process?
[00:04:10] Candidate: We implement a Dead Letter Queue (DLQ) pattern with exponential backoff and jitter. This prevents head-of-line blocking for subsequent valid messages while allowing our alerting system to notify on-call engineers for manual inspection and replay.
